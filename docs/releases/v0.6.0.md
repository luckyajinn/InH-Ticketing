# v0.6.0: The deployment package (milestone 6)

**Date:** 2026-11-09
**Branch:** `release-v0.6.0` (built with `milestone-6-deploy`)

Everything needed to run InH-Ticketing on the internal server at
`https://helpdesk.mckennalabs.com`: an HTTPS proxy, production security
settings, nightly backups with a tested way back, and guides for whoever builds
and runs the server.

It's released before the server exists. The same Docker setup has already run
on a test VM for a load test (below), so the first real install should mostly
be about the server, the certificate and Microsoft 365, not the app.

No screens changed in this version, so there are no new screenshots.

## HTTPS in front of the app

A **Caddy** reverse proxy (pinned to 2.11.9) now sits in front of the app and
is the only thing reachable from the network:

- It serves HTTPS with the certificate from the McKenna Labs **internal CA**,
  read from `/srv/inh-ticketing/certs` on the server. It never asks a public
  service for a certificate.
- Plain HTTP on port 80 is redirected to HTTPS.
- **HSTS:** once a browser has used the site over HTTPS, it refuses plain HTTP
  and certificate warnings can't be clicked past.
- Uploads of up to 60 MB are buffered at the proxy, so a slow upload can't tie
  up the app.
- The app's own port (8000) is no longer published.

Django adds a second line of defence: with `DEBUG` off it redirects HTTP to
HTTPS and sends HSTS itself, while Docker's health check (`/healthz`) keeps
working. `manage.py check --deploy` reports no issues.

## Backups and restores

`scripts/backup.sh` runs nightly from the server's cron:

- a **database dump**, read back after it's written to prove it's usable;
- an **attachments snapshot**. Unchanged files are hard links to the previous
  night's, so 14 days of backups take about one copy of the attachments, not 14.
  An 80 GB disk lasts five years or more at the expected rate.
- checksums for every file, a manifest, deletion of backups older than 14 days,
  and a warning when the disk is 80% full.

`scripts/restore.sh` checks the checksums and asks you to type the backup's
name to confirm. It takes a safety backup first, then restores into a new
database and swaps it in only if that worked. Then it restores the attachments
and compares them file by file.

## Tested on a test VM

On 2026-11-09 the production Docker setup ran on a Debian 13 test VM, with the
app held to the planned server's size (2 CPUs, 4 GB). This used the separate
`stress-test` branch: fake data, a self-signed certificate, and no Microsoft 365
or email.

| Test | People at once | Average response | 99% within | Failed |
|---|---|---|---|---|
| Normal busy period | 35 | 11 ms | 25 ms | 0 |
| Very busy | 100 | 10 ms | 24 ms | 0 |
| Find the limit | up to 400 | 16 ms | 67 ms | 0 |

About 125,000 requests in all. CPU averaged 2%, 12% and 42% of the 2 CPUs, and
memory stayed under 0.75 GB. The targets were an average under 20 ms and 99%
within 1 second.

What the test VM didn't cover is listed at the top of
[docs/deployment.md](../deployment.md): the internal-CA certificate, port 80's
redirect, backups under cron, and Microsoft 365 and email from the server.
