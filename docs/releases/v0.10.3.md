# v0.10.3: The worker's heartbeat

**Date:** 2026-11-11
**Built on:** `main`
**Released in:** [v0.10.4](v0.10.4.md). v0.10.3 has no release of its own: install
v0.10.4, which includes the heartbeat.

The last item built for v1.0.0: Reports can now say for sure whether the
background worker is running, instead of guessing.

## Why

The worker is the second program on the server, next to the web app. It sends
the queued emails every 15 seconds, reads the help-desk inbox every minute
(once email-in is on) and closes resolved tickets once an hour. If it stops,
the website keeps working, so nobody notices until someone says they never
got an email.

Until now, Reports noticed only when an email had been waiting over
2 minutes. On a quiet evening or weekend there's nothing waiting, so it stayed
green. A mailbox that couldn't be read, or an auto-close that failed, showed
only in the worker's log.

## What's new

**The heartbeat.** The worker saves what it last did in the database (one
row, updated each round): when it started, when it last finished a round,
its last inbox read and whether every mailbox could be read, and its last
auto-close with how many it closed.

**Reports → *Email and safety checks*** now starts with the worker:

| What happened | What Reports says |
|---|---|
| A round finished in the last 5 minutes | "The worker is running: last seen under a minute ago." with when it started |
| No round for 5 minutes | "The worker may have stopped: last seen 3.0 h ago. Until it's back, no emails go out, the inbox isn't read and resolved tickets don't close." |
| No round recorded yet | "No sign of the worker yet" |
| A mailbox couldn't be read | Under *Email in*: "The last read, at 10:42 AM, failed: emails may be waiting in the Inbox", the mailbox's address and the error, and when it was last read without a problem |
| Auto-close failed | Under *Auto-close*: "The last run, at 12:12 PM, failed", with the error |

*Email in* and *Auto-close* also show when they last ran. If an email is
overdue while the worker is running, *Email out* says so and points to the
worker's log, rather than saying the worker stopped.

Naming the mailbox matters once each department has its own: if
Mechanics' mailbox loses its permission, the others keep being read, and
Reports says which one failed.

**Docker's health check.** The `worker` container now has its own health
check, `python manage.py check_worker`, run every minute. `docker compose ps`
shows the worker as `(healthy)`, or `(unhealthy)` when it hasn't finished a
round in 5 minutes (after 3 failed checks in a row). Run it by hand too:

```bash
docker compose -f compose.yaml -f compose.prod.yaml exec worker python manage.py check_worker
```

The heartbeat never stops the worker: if it can't be saved (say the
database is briefly down), the worker logs it and carries on.

## Documentation

- Deployment guide: the worker shows `(healthy)` after an install or update;
  a troubleshooting row for `(unhealthy)`.
- Email setup: a mailbox that can't be read shows in Reports too. Fixed: a
  change to `.env` needs `up -d`, not a restart.
- Pilot checklist: stop the worker for 6 minutes and watch Reports.

## Upgrading

Follow [deployment.md](../deployment.md), section 10, with `v0.10.3`.
Migration `notifications` 0002 runs when the `web` container starts. Nothing
to do in `.env`. After `up -d --build`, `docker compose ps` should show
`worker` as `(healthy)` within a minute or two.

Rolling back to v0.10.1: undo the migration first, then check out and
rebuild:
`docker compose -f compose.yaml -f compose.prod.yaml exec web python manage.py migrate notifications 0001`.

## Tests

427 automated tests, all passing. The new ones cover: a round records the
start, the round and auto-close; a failed auto-close, and the next good run
clearing it; a good inbox read; an unreadable mailbox named once; one
mailbox failing while the others are read; any other inbox failure and
recovery; a long error cut short; a heartbeat that can't be saved not
stopping the worker; the 5-minute limit, longer for a slow worker;
`check_worker` for never, running and stopped; and each Reports message,
with the error text escaped.

In a browser, on demo data: the running worker after one round, then a
worker last seen 3 hours ago with a failed auto-close; no errors in the
console. `check_worker` exited 1 for the stopped worker. Not tried on Docker
here: the health check's first real run is the server's update.
