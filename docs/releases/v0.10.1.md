# v0.10.1: Category lists follow the department, and IT's common requests

**Date:** 2026-11-11
**Built on:** `main`

Two small changes before v1.0.0, plus documentation decisions: phones and the
restore drill are out.

## Category lists follow the department

Wherever a department is chosen, only its categories are offered:
- **The queue (admins):** choose Mechanics, and the category filter lists only
  Mechanics' categories. Changing the department clears the category chosen
  before. With **All departments**, the categories are grouped under their
  department's name. A category from another department in the address is
  ignored, rather than showing no tickets.
- **New request:** picking a common request fills in its category, and the
  category list then shows only that team's categories: after a Mechanics
  request, only Mechanics. Choose another of them and it's kept. **None, I'll
  type my own subject** brings every category back. The server holds to the
  same rule, so another team's category can't be sent with the request.
- **The admin site's ticket list:** with a department chosen, the category
  filter lists only its categories. Without one, each category shows its
  department ("IT: Hardware", "Mechanics: Mechanics").

Already working this way, unchanged: a department agent's own queue, the
category on a ticket's page (its own department's only, so a move between
departments stays an admin's **Move**), and Reports (categories follow the team
filter).

## Common requests for IT

New request now offers these under IT's categories:

| Category | Common requests |
|---|---|
| Hardware | Printer won't print, is jammed or shows offline · Printer needs toner or a new cartridge |
| Access | Forgot my password or locked out of my account · Password expired or needs changing |
| Network | Can't connect to the Wi-Fi · Wi-Fi is slow or keeps dropping |

None of them sets off the password warning. Admins change them in **Admin →
Categories**, one per line. Migration `tickets` 0009 adds them only to a
category whose list is empty, so a list an admin already set up is kept.

## Documentation

- **Phones aren't supported** (decided 2026-11-11). The web page is for
  company PCs; from a phone, people email their request. The deployment guide's
  phone steps are gone. Its section 1.6 keeps the DNS record, the staff Wi-Fi's
  DNS and blocking the guest Wi-Fi. The pilot checklist tests email from a
  phone's mail app instead.
- **No restore drill** (decided 2026-11-11). Deployment guide section 9 is now
  *Restoring a backup*: the steps, with no practice restore required. The
  backlog notes that the risk assessment asked for one tested restore before
  go-live, for the compliance lead to confirm.
- **The pilot checklist** covers this version's changes.

## Upgrading

Follow [deployment.md](../deployment.md), section 10, with `v0.10.1`.
Migration `tickets` 0009 runs when the `web` container starts. Nothing to do
in `.env`.

Rolling back to v0.10.0d: undo the migration first, which takes out IT's common
requests where they're unchanged, then check out and rebuild:
`docker compose -f compose.yaml -f compose.prod.yaml exec web python manage.py migrate tickets 0008`.

## Tests

400 automated tests, all passing. The new ones cover:
- the queue: a department's categories only, grouping under All departments,
  another department's category ignored, agents' own lists, an IT-only install
- New request: the department of each category and request on the page,
  another of the pick's department's categories kept, another department's
  replaced by the pick's
- IT's common requests: on a new install, an admin's own list kept, none sets
  off the password check
- the admin site's ticket list: the category filter follows the department

In a browser: picking a Mechanics request leaves only Mechanics in the
category list, a printer request leaves IT's five, and "None" brings all seven
back; the queue and the admin site's filters as above; no errors in the console.
